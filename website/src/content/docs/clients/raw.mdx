This page is for people writing their **own** client, porting one to a new language, or debugging an existing one. Everything a library does is shown here explicitly. For a bot, use a [client library](/clients/) instead.

## 1. Open the WebSocket

```
GET ws://HOST:2333/v4/websocket
Authorization: youshallnotpass
User-Id: 123456789012345678
Client-Name: my-client/0.1.0
Session-Id: <previous id, optional>
```

Failure modes: wrong password → HTTP 401 and no upgrade; too many connections from one IP → HTTP 429; messages over 64 KiB → silently dropped; a malformed frame → close code `1008`.

## 2. Get voice credentials from Discord

Your bot sends **Gateway op 4** on the shard that owns the guild:

```json
{ "op": 4, "d": { "guild_id": "G", "channel_id": "C", "self_mute": false, "self_deaf": true } }
```

Discord answers with two dispatches. You need three values from them:

| Dispatch | Field | Player update field |
|---|---|---|
| `VOICE_STATE_UPDATE` (for your bot's user id) | `session_id` | `voice.sessionId` |
| `VOICE_SERVER_UPDATE` | `token` | `voice.token` |
| `VOICE_SERVER_UPDATE` | `endpoint` | `voice.endpoint` |

They can arrive in either order. Wait for both, then continue. A `VOICE_SERVER_UPDATE` with `endpoint: null` means Discord is migrating the voice server — wait for the next one.

## 5. What comes back on the socket

```json
{"op":"event","type":"TrackStartEvent","guildId":"G","track":{"encoded":"…","info":{…}}}
{"op":"playerUpdate","guildId":"G","state":{"time":1757000000000,"position":5012,"connected":true,"ping":48}}
{"op":"event","type":"TrackEndEvent","guildId":"G","track":{…},"reason":"finished"}
{"op":"stats","players":1,"playingPlayers":1,"uptime":81234,"memory":{…},"cpu":{…},"frameStats":{…}}
```

Every message shape is listed in the [WebSocket reference](/api/websocket/).

## 6. Leave

1. Send Gateway op 4 with `"channel_id": null` so Discord disconnects the bot.
2. `DELETE /v4/sessions/{sessionId}/players/{guildId}` → `204`.

Closing the WebSocket without resuming enabled destroys every player of that session automatically.

## Resuming

```bash
curl -X PATCH "http://localhost:2333/v4/sessions/$SESSION" -H 'Authorization: youshallnotpass' \
  -H 'Content-Type: application/json' -d '{"resuming":true,"timeout":60}'
```

Reconnect within `timeout` seconds sending `Session-Id: $SESSION`. The `ready` message says `"resumed": true` and is followed by up to 100 buffered events you missed. After the timeout, the session and its players are gone and a fresh session ID is issued.

## Client-to-server ops

Standard Lavalink v4 clients never *send* on the WebSocket. KizunaLink additionally accepts these JSON messages (all need `guildId` except `ping`):

```json
{"op":"ping"}                                            → {"op":"pong"}
{"op":"updatePlayer","guildId":"G", ...PlayerUpdate body}
{"op":"queueTrack","guildId":"G","encoded":"QAAA…"}
{"op":"skipTrack","guildId":"G"}
{"op":"previousTrack","guildId":"G"}
{"op":"loop","guildId":"G","mode":"queue"}               // none | track | queue
{"op":"autoplay","guildId":"G"}                          // toggle
{"op":"shuffleQueue","guildId":"G"}
{"op":"clearQueue","guildId":"G"}
{"op":"destroyPlayer","guildId":"G"}
```

They exist so a bot can drive KizunaLink with a single socket and no REST at all. Details in [Extensions](/api/extensions/).

## Checklist for client authors

- Send `Authorization` as the **bare password**. No `Bearer`, no base64.
- Always send `User-Id`; KizunaLink uses it in voice payloads.
- Treat `sessionId` as opaque; it's a random hex string, not a UUID.
- Handle `WebSocketClosedEvent` codes `4006`, `4009`, `4014`: re-send the voice state (4006/4009) or destroy the player (4014 = kicked/disconnected).
- `ping: -1` in `playerUpdate` means not connected yet.
- Send `noReplace=true` when queuing so a race doesn't cut off the current track.
- Rate limits: `429` with `Retry-After` — back off per node, not per guild.
